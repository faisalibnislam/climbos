# Selected sales opportunity review — 17 November 2026

## Requirement and audited behavior

Original requirements 113 (qualification), 114 (follow-up), and 115 (conversation quality) remain partial. Book 11's discovery, qualification, buyer-progress and read-only opportunity-review route informed this extension. Its larger proposed CRM/event architecture was not assumed to exist.

The current CRM already stores owner notes, optional loss reasons, next-step text/date and stage. The customer-progress sheet exposes those notes. Stage-attention heuristics and aggregate sales-learning context already exist. However, the in-app assistant's `get_pipeline` returned only a bounded summary of names, stages, values and next steps: it omitted record ids, notes and loss reasons. The assistant could not reliably inspect the specific customer's saved needs or objections when asked what to do next.

## Implemented path

1. Customer progress → open a record → **Review next step** prepares an editable question in the existing Climb AI composer and attaches the selected deal id. The sheet closes. Existing unsent question text remains; no chat is submitted and no model run is started by the shortcut. The owner can edit the question before sending it through the normal metered chat path.
2. `get_pipeline` retains its existing overview and now returns deal ids. Its optional `dealId` input calls the new read-only `crm.detail` query. Both in-app chat and the existing MCP tool registry use the same caller-scoped query; no new agent or provider was added.
3. The query independently checks workspace access and deal ownership. It reads the exact selected record even if that record is older than the overview's 500-row limit. It returns current stage, owner-reported value/currency, next step, recorded close/stage dates and optional loss reason, plus two saved notes per page. It omits email addresses and note-author ids.
4. Context is labeled recorded CRM information. Values are separately owner-reported. Notes with an author are labeled owner-reported; authorless entries remain recorded context because booking/outreach/import activity may have created them. Neither is a verified transcript, proof of willingness to buy or permission to contact.
5. Earlier-note pages require the initial content hash and position. A changed record invalidates pagination even when edits share the same millisecond. Returned note positions refer to that version; missing/invalid dates remain unknown. History coverage states how many notes remain stored, the next page and the existing rolling 200-note retention limit. The existing tool-output size limit can still return a clearly labeled preview for oversized records.
6. The actual chat loop validates the typed tool result and wraps it as untrusted data, escaping text that could close the wrapper. Assistant guidance requires reading relevant notes, distinguishing evidence from inference, surfacing contradictions, checking the buyer's need/obstacle/decision process, and considering a next question, draft, wait or respectful stop. Missing evidence is not a failed qualification; stage, delay or a price objection alone does not justify a discount or probability claim.
7. New next-step dates are deterministically validated before saving. Invalid legacy dates stay unknown in both the board query and assistant overview instead of crashing ISO formatting. No historical date is guessed or rewritten.

The read path creates no approvals, sends, scheduled actions or CRM updates. Existing consequential tools still require their normal scoped confirmation and permissions. The plan-engine version and runtime model routes are unchanged; this assistant-tool extension does not invalidate unrelated saved plans.

## Verification and limits

See [Verification](../Verification.md) for commands and counts. Regressions exercise actual queries, selected records outside the board bound, note pagination/version changes, cross-workspace denial, missing/invalid dates, source distinctions, untrusted content and the real chat tool loop with a mocked model. Existing CRM/assistant/approval/tenant tests are included. Desktop/mobile tests verify an editable question, preserved unsent text, no record/action/chat side effects, no horizontal overflow and no serious/critical automated accessibility findings. These scans are not full accessibility conformance. The mobile screenshots were visually inspected.

The first four new tests failed against the old code. A TypeScript issue in the test caller adapter was corrected. The first browser scan ran during the sheet's fade animation and reported transient contrast failures; waiting for the actual animation to finish made both viewports pass without changing colors or disabling the scan.

No live model or customer conversation was evaluated. The test model proves routing and evidence transport, not the quality or faithfulness of generated advice. The assistant can still make interpretive mistakes; no automatic structured qualification, calibrated close probability, complete conversation transcript, retained stage-event history or automatic follow-up was added. Notes older than retained history are unavailable. The eight-turn assistant limit and output cap can prevent exhaustive review of a long record; the instructions require disclosing that limitation. The overview still lists only its bounded set; exact-id lookup does not create an unlimited search UI. This is a usable extension to the existing sales-review path, not completion of requirements 113–115 or the full project.
