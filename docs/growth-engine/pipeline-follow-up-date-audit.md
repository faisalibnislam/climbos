# Sales follow-up dates and stage age — 17 November 2026

## Confirmed gaps in the existing path

The audit followed Book 11's buyer-progress route and the real path from CRM writes and automatic booking/outreach synchronization to `crm.list`, `inbox.attention`, the pipeline cards/editor, Today and `get_pipeline`. Existing manual stage changes already recorded stage time; missing legacy stage time was intended to remain unknown. The corpus's broader proposed sales intelligence is not implemented merely by these changes.

The date picker saved an implicit 09:00 in the browser timezone but loaded it using UTC. The overdue function waited a fixed 24 hours after that instant, rather than comparing calendar days in the workspace timezone. Invalid/future stage times could be presented as known. Automatically created booking/outreach deals and cancelled-call stage changes omitted the stage timestamp. Today and the board also read different bounded sets of deals.

## Implemented path

1. New owner-selected next-step dates are stored as `deals.nextStepDate`, a validated Gregorian `YYYY-MM-DD`, separately from appointment/legacy `nextStepAt` instants. The existing update mutation accepts either representation, rejects simultaneous input, and clears the other representation when the owner replaces or clears a date. Existing edit permissions and tenant checks remain in force. Historical instants are not migrated or guessed.
2. Shared deterministic helpers validate dates, instants and timezone, convert an instant to its workspace calendar date, and compare that date to the current workspace day. Today is not overdue; a previous day is. Unknown/invalid timezone, invalid clock/date and conflicting representations yield timing uncertainty rather than a deadline. Invalid or future stage timestamps yield unknown age; no edit/creation timestamp is substituted for missing stage history.
3. Stage age continues to use elapsed 24-hour days and the existing review policies (21 for leads, 14 for talking/booked). It is not buyer intent or a calibrated sales prediction. New automatic deal creation and existing cancellation transitions now record stage time. Repeated same-stage synchronization and unrelated edits do not reset it. Existing automatic prospect synchronization rejects a foreign-tenant deal; cancellation updates check deal/prospect tenancy.
4. The board and Today use the same helper and newest 500-record sample. The 501st record detects partial coverage; Today qualifies counts as “at least” when capped. The board exposes the timezone, a timing-unknown badge where applicable, and a concise explanation of date/stage-age prompts. Today links overdue/stage-age review to customer progress without contacting anyone.
5. The editor saves the selected calendar date directly, can clear it, and explains that this changes a CRM next step only. Legacy appointment instants are displayed as dates in the current workspace timezone, not as a recovered original owner-selected date. Errors leave the previous displayed date intact. Saving does not reschedule a booking or send a message.
6. The existing assistant overview and exact-record output contracts include date-only fields, timezone and computed attention. This prevents the assistant from losing dates merely because no timestamp is present. Output guidance distinguishes review prompts from evidence of buyer interest or permission to follow up. No new agent, provider or plan-engine version is introduced.

## Evidence and remaining limits

[Verification](../Verification.md) records the actual commands. The final focused run passed 69 tests across twelve files, including DST transitions, opposite-side timezone dates, malformed/conflicting/unknown input, valid leap day, invalid/future stage history, date replacement/clear, stage-clock preservation, newest-record coverage, booking cancellation and existing approval/tenant boundaries. Typecheck and scoped lint passed. Four desktop/mobile checks passed: save/reopen/clear with Honolulu browser and Dhaka workspace timezones, plus the existing selected-record assistant flow. No approval, booking, email, workflow or chat was created by the date UI. No horizontal overflow or serious/critical automated accessibility findings; this is not full accessibility conformance. The mobile date-editor screenshot was visually inspected.

The initial browser checks found a new custom accessible-name override that omitted the visible date. It was removed, preserving the existing labeled picker and accessibility scan, before the passing run. No live model or provider was called. Only the isolated loopback backend was synced; no hosted deployment occurred.

These are query-time observations, not a continuously ticking deadline monitor; cached/open views can age until data is checked again. The configured workspace timezone is an operational setting, not proof of customer geography. Existing timestamp records cannot recover the timezone/date originally intended by the owner. Stage history still retains only the latest transition time. The subsequent [booking identity repair](booking-deal-identity-audit.md) replaces name/time matching for new bookings and preserves multiple appointments; ambiguous historical links and full stage-event history remain incomplete. Review thresholds remain explicit heuristics. Automatic personalized follow-up, response-based learning and expert advice quality remain incomplete. Requirements 114/239 and the full project are not marked complete by this batch.
