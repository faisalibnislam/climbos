# Buying-context evidence for selected sales opportunities — 17 November 2026

## Confirmed gap and reading route

Requirements 81–90 and 113–115 concern customer needs, buying obstacles and useful sales review. The existing path already supported owner CRM notes, loss reasons, date-only next steps, exact selected-record lookup, version-bound note pagination and an editable assistant-review request. Its review instructions asked for qualification evidence, but there was no structured owner input or read contract for that evidence. A booking or pipeline stage could not establish qualification. This batch adds that missing evidence workflow rather than a new sales agent or automatic score.

Read `AGENTS.md`, the growth-intelligence master index, Book 11's opportunity/discovery/qualification and execution sections, and the installed Next.js server/client guide. The book is a design reference, not proof of runtime behavior. No external platform integration, policy or pricing claim was introduced.

## Implemented path

1. **Customer progress → selected record → Buying context** opens a lazily queried section. Six optional topics cover the customer's problem, desired outcome, fit/delivery constraints, decision process, timing/readiness, and alternatives (including waiting). Missing topics remain unknown; no completion score, mandatory sales framework or qualification verdict is generated.
2. An editing member records one short observation, its described source, an actual observation date and one of reported/conflicting/outdated/unknown. All entries remain **owner-reported**, even if the source description mentions analytics or a customer document. Sources are descriptions, not fetched or independently verified documents. Dates must be real, on/after 1970 and no later than today in UTC. There are no invented deadlines or default observations.
3. `crm.recordQualification` validates tenant membership, edit permission, exact deal ownership, input lengths and the expected qualification revision. Concurrent edits fail without overwriting the draft. Corrections retain actor, recording time, observation date and monotonically increasing revision. The six latest topic reports remain available independently of the rolling 20-entry history; the UI exposes that retention limit and total revision count.
4. `crm.qualification` is a read-only exact-record query with the same whole-deal version hash as `crm.detail`. The existing `get_pipeline` tool accepts `view=qualification`; the assistant is instructed to read it with the selected deal and original notes version. A changed record rejects mixed-version review. The separate bounded view preserves complete reports without crowding out paginated notes. Author ids and history are omitted from the assistant's current-report output; source labels, dates, states and explicit unknowns are preserved and encoded as untrusted context.
5. **Review next step** still prepares an editable question and selected deal in the shared composer; it does not submit. The actual assistant tool loop can retrieve these reports and its instructions require distinguishing evidence from interpretation, exposing conflicts and asking only decision-relevant questions. It must not turn completeness into a score or assume old reports are current. The model and routing remain unchanged.
6. Saving evidence only updates the selected deal's qualification data/update time and records an audit event. It does not change stage, possible value, consent, next-step schedule, bookings, approvals, messages or billing. The read tool has no mutation authority.
7. Reports are nested in existing deal records, so removing the deal or purging its workspace removes retained qualification history too. Workspace export now includes a bounded recent deal page (up to 500 records, approximately 1 MB of reads) and explicit coverage/limit fields. Other tenants remain isolated. The existing contact-list deletion operation is separate: deleting an email contact does not currently delete a CRM opportunity. Use the existing deal removal or workspace deletion path for those records; this batch does not claim universal identity resolution or erasure across every source.

## Verification and remaining limitations

See [Verification](../Verification.md) for final commands and counts. Regressions cover every report state, unknown legacy records, invalid dates/lengths/revisions, corrections and history bounds, complete tool output at maximum field lengths, untrusted content, the actual assistant tool loop with a mocked model, cross-tenant denial, viewer/anonymous write denial, stale/mixed-version reads, export bounds, record removal and workspace purge. Assertions confirm no consequential records or stage changes are produced. Browser checks enter and correct reports, inspect history, prepare an editable question, and check form/review accessibility, overflow and page errors.

This is a manual evidence input and review capability, not automated conversation extraction, transcription, independent source verification, semantic contradiction detection, a calibrated close probability, or validated advice quality. Reports are not automatically refreshed or judged stale after an arbitrary age. The assistant's actual use and interpretation can vary; fixtures prove transport and enforcement, not professional judgment or sales effectiveness. Qualification history is bounded, and no aggregate qualification statistics are fed into growth forecasts. No live model evaluation, customer contact or hosted deployment was performed. The full project and broad requirements remain incomplete.
