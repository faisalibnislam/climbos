# Customer-progress eligibility for email review

17 November 2026. Follow-up to original requirements 111/118/148/386 and the owner's evidence, customer relevance and exact-approval instructions. Read AGENTS.md, the master-index route, Book 08 sections on scoped lifecycle states, onboarding exits and meaningful outcomes, and the installed Next.js client/server component guide. The library describes desired behavior; it was not treated as implementation proof.

## Existing path and confirmed gap

The existing owner workflow records dated, attributed observations for an uploaded contact in a named product/journey. `planningEmailAudience` already groups bounded observations; `customerProgressBrief` and the actual retention job expose their historical, owner-reported status. Retention runs retain an original input checkpoint and evidence snapshot. Originating growth-plan context already preserves the intended lifecycle purpose when creating email drafts.

Execution was separate: `EmailSendPanel` selected a static contact segment; `marketing.approveSend` bound the approved artifact, sender, exact opted-in recipient set, destination, credential, allowance and policy. `claimSend` and `authorizeSendDispatch` recomputed that segment and checked consent, suppression, contact pressure and approval. Customer progress was not an eligibility input. A newly completed milestone could therefore leave someone in the audience of a setup reminder.

## Implemented workflow

1. The existing email send form offers **Limit this email by customer progress**. It is optional and off initially. Groups come from usable observations in the selected opted-in audience; the owner selects the product/journey, known stage and its exact recorded definition. No synonym, segment name, open or click is substituted for that definition.
2. The owner chooses the oldest acceptable observation, from 1 to 365 UTC calendar days. No value is supplied automatically. Age is calculated from the recorded calendar date to today's UTC date; a report exactly the selected number of days old qualifies. This is a recency policy, not proof that the reported state is still true.
3. `marketing.emailAudiencePreview` returns the qualifying count, the opted-in segment count, categorized exclusions, the normalized rule and a preview hash. Missing, unknown, conflicting, malformed, future or unrelated-scope reports cannot qualify. Different stages or definitions and outdated reports are excluded explicitly. No raw contact names, emails or narrative evidence are returned by this preview; owner-authored group names/definitions remain visible to authorized workspace members.
4. The approval requires the exact current preview hash when a rule is used. It stores that rule inside the existing hashed approval scope. Each selected recipient contributes its progress-record identity and a hash of the particular observation supporting eligibility. This is in addition to the existing exact recipient, consent and artifact binding.
5. The same deterministic rule runs again before provider preparation and immediately before send dispatch. A change to the qualifying set or its supporting observation invalidates the whole send and releases its reserved allowance through the existing failure path. It does not silently replace recipients or send to a reduced list under the old approval. An unrelated product/journey update does not invalidate the original observation.
6. Contact-frequency checks use the filtered audience, so an excluded contact's recent email does not block this send. Consent, suppression, workspace/role checks, content version, provider destination, credentials and budget remain independent requirements. A known lifecycle state never grants permission.
7. The confirmation shows the captured count and rule. A changed preview disables confirmation and asks for fresh review. A rule must be complete and yield at least one recipient before Send is enabled. A disappeared selected group remains visible while the count updates, rather than silently selecting another group.
8. The shared planning brief now accurately describes this available per-send filter while retaining its historical-evidence warnings. The actual retention writer boundary is tested for this capability description. Advice does not choose the owner's freshness threshold or authorize sending.

## Provider and compatibility behavior

No agent, provider, external API or background enrollment system was added. The existing Resend integration still requires its external list to match the approved filtered audience exactly. Extra provider contacts stop the send; this feature does not unsubscribe or remove them automatically. Owners must prepare a matching list using their provider's existing setup. Original contacts/list preparation may already have occurred when a late progress change prevents dispatch; those provider changes are not automatically rolled back.

Unfiltered sends retain their existing recipient representation and approval binding. Historical approvals without a progress rule are not retroactively converted into lifecycle approvals. Existing uploaded-contact observation, correction, export and deletion behavior is reused. This change adds no new personal-data table. Exact rule and recipient/evidence hashes persist with the approval; original narrative observations remain subject to the existing bounded contact-progress history, so hashes alone do not reconstruct every old report.

## Remaining work and honest limits

This is a complete optional per-send path over owner observations, not automatic lifecycle enrollment, product telemetry, event ingestion, account/subscription modeling, an adaptive cadence algorithm or continuous monitoring. A progress change after dispatch authorization cannot recall an email. Browser checks use a credential-free local fixture; provider sends are mocked in backend tests. No live email, paid model, hosted deployment or real-world conversion/retention lift was tested.

The UI lists up to 30 distinct usable groups and discloses omitted groups; a narrower segment is needed to review further groups. The existing bounded marketing audience/consent reads remain in force, and large-audience performance has not been validated. Date-only freshness cannot establish hour-level recency. The full 410 requirements and later owner specifications remain active and incomplete.
